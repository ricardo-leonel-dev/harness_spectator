## Specific things worth flagging

### CORS behavior change (none observed)

The `tower-http` 0.5 → 0.7 bump was the highest-risk bump in this feature (zero test coverage on
CORS, spans two majors). I diffed the `CorsLayer` builder API between the two installed versions
(`/Users/ricardoaguilar/.cargo/registry/src/.../tower-http-0.5.2/src/cors/mod.rs` vs
`.../tower-http-0.7.0/src/cors/mod.rs`): `CorsLayer::new()`, `allow_origin(HeaderValue)`,
`allow_methods([Method])`, and `allow_headers([header])` are structurally identical (same `pub fn`
signatures, same generic constraints, same `Access-Control-Allow-Origin` / `-Methods` /
`-Headers` semantics). The current `backend/src/app.rs` configuration compiles unchanged against
0.7, produces the same response headers as before for the same inputs, and is invoked by all five
integration tests in `tests/harness.rs` (every `oneshot(req)` flows through the layer stack).

**No observable CORS behavior change.** The follow-up CORS regression test feature the leader
mentioned is still useful (no existing test asserts the actual `Access-Control-*` headers on the
response), but it's not protecting against a behavior change introduced by this feature — it
would be net-new coverage. Worth confirming with the leader before that follow-up is scoped.

### `thiserror` lockfile order (resolved cleanly)

`design.md` flagged that `thiserror` could appear twice in `Cargo.lock` (once as this project's
own `"2."` direct dep, once as a transitive `"1.x"` pulled in by some other crate) and that the
test would need a second anchor if the first-occurrence-by-name lookup hit the wrong stanza. In
the regenerated `Cargo.lock`, only ONE `[[package]] name = "thiserror"` stanza exists (version
2.0.20, line 1978); all other `thiserror` mentions are dependency references to that one stanza.
So `.find("name = \"thiserror\"\n")` lands on the right one, no adjustment needed — T7's
fallback clause was unused.

### `sqlx` feature-rename (no source changes needed)

`sqlx::query_as` / `sqlx::PgPool` / `sqlx::FromRow` / `sqlx::query!` / `sqlx::test` are all
unchanged between 0.7 → 0.9 at the API surface this codebase uses. The only required edit was
the feature-list split (`runtime-tokio-rustls` → `runtime-tokio` + `tls-rustls`), as the spec
predicted. `backend/src/harness/reader.rs` (178 LOC, the biggest `sqlx` user) and the 5
`#[sqlx::test]` integration tests both compile and run unchanged.

### `jsonwebtoken` 9 → 11 (no source changes needed)

`Validation::new`, `set_audience`, `validate_exp`, `DecodingKey::from_secret`, `decode::<Claims>`,
`Header::new`, `EncodingKey::from_secret`, `encode` — all signatures identical between 9 and 11 for
the call patterns this codebase uses. `features = ["rust_crypto"]` adds on top of the default
`use_pem` feature (Cargo only respects `default-features = false` for that), pulling in
`pem v3` + `simple_asn1 v0.6` — harmless, design.md explicitly leaves this alone.

### `thiserror` 1 → 2 (no source changes needed)

`#[derive(Error)]` on `ApiError` (plain enum, `#[error("...")]` messages, no `#[from]`,
no field interpolation beyond what 1.x already supported) compiles unchanged. Verified by
`cargo build`/`cargo clippy --all-targets` clean.

### Edition 2024

**Not migrated.** `backend/Cargo.toml` keeps `edition = "2021"` per `design.md`'s
"Deferred: edition 2024" section. `rust-version = "1.94"` is edition-2024-compatible (2024's
own MSRV is 1.85) so a future feature can take that on without revisiting the floor.
